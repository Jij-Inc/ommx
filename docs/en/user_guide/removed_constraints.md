# Removed Constraints and Feasibility

Rather than simply deleting a constraint from a model, OMMX can move it from the active to the removed stage of its lifecycle. A removed constraint is excluded from the current mathematical problem sent to the Backend, but OMMX retains the pre-transformation constraint and the reason for its removal so that {class}`~ommx.Solution` and {class}`~ommx.SampleSet` can evaluate it.

This lets a prepared Instance expose only an Adapter's exact input as active structure while still checking whether a returned solution satisfies the constraints that existed before transformation. See [Instance Preparation and `PreparationPolicy`](./preparation_policy.md) for the responsibility boundary of Preparation as a whole.

## Active and Removed

Each of the regular, Indicator, OneHot, and SOS1 constraint families has its own active and removed collections. Active and removed IDs do not overlap within a family, and context such as labels and provenance is preserved when a constraint moves through the lifecycle.

| Constraint family | Active | Removed |
|---|---|---|
| Regular | {attr}`~ommx.Instance.constraints` | {attr}`~ommx.Instance.removed_constraints` |
| Indicator | {attr}`~ommx.Instance.indicator_constraints` | {attr}`~ommx.Instance.removed_indicator_constraints` |
| OneHot | {attr}`~ommx.Instance.one_hot_constraints` | {attr}`~ommx.Instance.removed_one_hot_constraints` |
| SOS1 | {attr}`~ommx.Instance.sos1_constraints` | {attr}`~ommx.Instance.removed_sos1_constraints` |

A removed entry stores the original constraint together with `removed_reason` and `removed_reason_parameters`. The reason identifies the operation or application that moved the constraint to removed, while the parameters provide operation-specific string metadata.

The following example manually relaxes a regular constraint and lowers a OneHot constraint to a mathematically equivalent regular constraint.

```{code-cell} ipython3
from ommx import DecisionVariable, Instance, OneHotConstraint, ProvenanceKind

x = [DecisionVariable.binary(i, name="x", subscripts=[i]) for i in range(2)]
instance = Instance.from_components(
    decision_variables=x,
    objective=x[0] + 2 * x[1],
    constraints={10: x[0] <= 0},
    one_hot_constraints={20: OneHotConstraint(variables=x)},
    sense=Instance.MAXIMIZE,
)

instance.relax_constraint(
    10,
    "example.capacity_relaxation",
    ticket="OPS-42",
)
generated_id = instance.convert_one_hot_to_constraint(20)

assert 10 not in instance.constraints
assert instance.removed_constraints[10].removed_reason == "example.capacity_relaxation"
assert instance.removed_constraints[10].removed_reason_parameters == {"ticket": "OPS-42"}

assert 20 not in instance.one_hot_constraints
assert instance.removed_one_hot_constraints[20].removed_reason == (
    "ommx.Instance.convert_one_hot_to_constraint"
)
```

Regular constraints generated by lowering also record {attr}`Constraint.provenance <ommx.Constraint.provenance>` pointing back to their source. Because the removed entry identifies the generated constraints and each generated constraint identifies its source, both directions of a transformation can be audited. Follow the links from [Special Constraint Types](./special_constraints.md) to the API Reference for the exact generated artifacts, reason parameters, and lowering contract for each constraint family.

```{code-cell} ipython3
generated = instance.constraints[generated_id]
assert any(
    p.kind == ProvenanceKind.OneHotConstraint and p.original_id == 20
    for p in generated.provenance
)
```

Operations that transform regular constraints, such as penalty methods and removing trivially satisfied constraints, use the same removed lifecycle. {class}`~ommx.ParametricInstance` also retains active and removed collections for regular constraints.

## Auditing an Instance

{meth}`~ommx.Instance.constraints_df` selects a constraint family with `kind=`. With `removed=True`, it returns active and removed rows in one DataFrame and distinguishes them with `removed_reason` and `removed_reason.{key}` columns.

| `kind=` | Constraint family | Index |
|---|---|---|
| `"regular"` | Regular | `regular_constraint_id` |
| `"indicator"` | Indicator | `indicator_constraint_id` |
| `"one_hot"` | OneHot | `one_hot_constraint_id` |
| `"sos1"` | SOS1 | `sos1_constraint_id` |

```{code-cell} ipython3
instance.constraints_df(removed=True)
```

```{code-cell} ipython3
instance.constraints_df(kind="one_hot", removed=True)
```

Use {meth}`~ommx.Instance.constraint_removed_reasons_df` when you need reasons and parameters in long format.

```{code-cell} ipython3
instance.constraint_removed_reasons_df()
```

## `Solution.feasible` and `Solution.feasible_relaxed`

{meth}`~ommx.Instance.evaluate` evaluates both active and removed constraints. {attr}`~ommx.Solution.feasible` is `True` only if all of the following hold.

- Every active and removed constraint across all four constraint families
- Decision-variable kinds and bounds

{attr}`~ommx.Solution.feasible_relaxed` excludes removed constraints, but it still checks active constraints and decision-variable domains.

For the Instance above, evaluating `x[0] = 1, x[1] = 0` satisfies the active regular equality generated from the OneHot constraint but violates the removed constraint `x[0] <= 0`. The state is therefore feasible for the current relaxed problem but infeasible when the pre-transformation constraint is included.

```{code-cell} ipython3
solution = instance.evaluate({0: 1, 1: 0})

assert not solution.feasible
assert solution.feasible_relaxed
```

{meth}`~ommx.Solution.constraints_df` returns both active and removed rows as evaluated constraints, so it has no `removed=` argument. Add `"removed_reason"` to `include=` to attach the reason and parameters to rows that had been removed.

```{code-cell} ipython3
solution.constraints_df(include=("removed_reason",))
```

The same API works for Indicator, OneHot, and SOS1 by changing `kind=`. {meth}`~ommx.Solution.constraint_removed_reasons_df` is also available for reasons in long format.

## Evaluating Each Sample in a `SampleSet`

{meth}`~ommx.Instance.evaluate_samples` preserves the active/removed distinction for every sample. {attr}`~ommx.SampleSet.feasible` and {attr}`~ommx.SampleSet.feasible_relaxed` map sample IDs to results for the four constraint families: the former checks active and removed constraints, while the latter checks active constraints only. `best_feasible` and `best_feasible_relaxed` select samples using these constraint-only results.

These {class}`~ommx.SampleSet` results do not check decision-variable kinds or bounds. This differs from {attr}`~ommx.Solution.feasible` and {attr}`~ommx.Solution.feasible_relaxed`, which check the variable domains as well. When treating a selected sample as a final Solution, check feasibility on the Solution too.

```{code-cell} ipython3
from ommx import Samples

sample_set = instance.evaluate_samples(
    Samples(
        [
            {0: 1, 1: 0},  # Violates only the removed x[0] <= 0 constraint
            {0: 0, 1: 1},  # Satisfies both active and removed constraints
        ]
    )
)

assert sample_set.feasible == {0: False, 1: True}
assert sample_set.feasible_relaxed == {0: True, 1: True}
```

{meth}`~ommx.SampleSet.constraints_df` and {meth}`~ommx.SampleSet.constraint_removed_reasons_df` accept the same `kind=` and `include=("removed_reason",)` options as `Solution`.

## Relax and Restore Are Not Rollback

Regular and Indicator constraints support manual lifecycle changes through these owner operations.

- {meth}`~ommx.Instance.relax_constraint` / {meth}`~ommx.Instance.restore_constraint`
- {meth}`~ommx.Instance.relax_indicator_constraint` / {meth}`~ommx.Instance.restore_indicator_constraint`

Restore moves one removed constraint back to active. If the current Instance contains fixed values or decision-variable dependencies, OMMX first applies them to normalize the restored constraint. An Indicator constraint cannot be restored if its indicator variable is itself fixed or dependent.

Restore does not reverse an entire lowering or Preparation. It does not remove separate side effects such as generated regular constraints, auxiliary variables, penalties added to the objective, or decision-variable dependencies. OneHot and SOS1 have no public restore operation; after lowering, they remain as removed history.

```{code-cell} ipython3
instance.restore_constraint(10)

assert 10 in instance.constraints
assert generated_id in instance.constraints  # The generated constraint remains
assert 20 in instance.removed_one_hot_constraints

restored_solution = instance.evaluate({0: 1, 1: 0})
assert not restored_solution.feasible_relaxed
```

Likewise, restore cannot undo every partial mutation left when Preparation fails partway through. If you need to preserve the pre-transformation Instance, make an explicit copy before Preparation.
