# ommx.Solution

OMMX has several structures that represent the solution of mathematical models.

| Data Structure | Description |
| --- | --- |
| {class}`~ommx.State` | Holds the solution value for the decision variable ID. The simplest representation of a solution. |
| {class}`~ommx.Solution` | A representation of the solution intended to be human-readable. In addition to the values of the decision variables and the evaluation values of the constraints, it also holds metadata for the decision variables and constraints added to the {class}`~ommx.Instance`. |

Most solvers are software designed to solve mathematical models, so they return minimal information equivalent to `ommx.State`, but OMMX mainly handles `ommx.Solution`, which allows users to easily check the optimization results.

`ommx.Solution` is generated by passing `ommx.State` or equivalent `dict[int, float]` to the `ommx.Instance.evaluate` method. Let's consider the simple optimization problem we saw in the previous section again:

$$
\begin{aligned}
\max \quad & x + y \\
\text{subject to} \quad & x y  = 0 \\
& x, y \in \{0, 1\}
\end{aligned}
$$

It is clear that this has a feasible solution $x = 1, y = 0$.

```{code-cell} ipython3
from ommx import ConstraintID
from ommx import DecisionVariable, Instance, Sense

# Create a simple instance
x = DecisionVariable.binary(1, name='x')
y = DecisionVariable.binary(2, name='y')

instance = Instance.from_components(
    decision_variables=[x, y],
    objective=x + y,
    constraints={ConstraintID(0): x * y == 0},
    sense=Sense.Maximize
)

# Create a solution
solution = instance.evaluate({1: 1, 2: 0})  # x=1, y=0
```

The generated `ommx.Solution` inherits most of the information from the `ommx.Instance`. Let's first look at the decision variables.

```{code-cell} ipython3
solution.decision_variables_df()
```

In addition to the required attributes—ID, `kind`, `lower`, and `upper`—it also inherits metadata such as `name`. Additionally, the `value` assigned in `evaluate` is stored. Similarly, the evaluation value is added to the constraints as `value`.

```{code-cell} ipython3
solution.constraints_df(kind="regular")
```

The `objective` property contains the value of the objective function, and the `feasible` property contains whether the constraints are satisfied.

```{code-cell} ipython3
print(f"{solution.objective=}, {solution.feasible=}")
```

Since $xy = 0$ when $x = 1, y = 0$, all constraints are satisfied, so `feasible` is `True`. The value of the objective function is $x + y = 1$.

What happens in the case of an infeasible solution, $x = 1, y = 1$?

```{code-cell} ipython3
solution11 = instance.evaluate({1: 1, 2: 1})  # x=1, y=1
print(f"{solution11.objective=}, {solution11.feasible=}")
```

`feasible = False` indicates that it is an infeasible solution.

## Query constraints without pandas

`Solution.get_constraints(kind=...)` and `SampleSet.get_constraints(kind=...)`
return dictionaries of owned result snapshots. `kind` is a required keyword for
both `get_constraints` and `constraints_df` on these result objects.

```{code-cell} ipython3
from ommx import ConstraintID

rows = solution.get_constraints(kind="regular")
rows[ConstraintID(0)].violation()
```

The dictionary keys preserve the constraint family:

| `kind` | ID type | Solution value | SampleSet value |
| --- | --- | --- | --- |
| `"regular"` | `ConstraintID` | `EvaluatedConstraint` | `SampledConstraint` |
| `"indicator"` | `IndicatorConstraintID` | `EvaluatedIndicatorConstraint` | `SampledIndicatorConstraint` |
| `"one_hot"` | `OneHotConstraintID` | `EvaluatedOneHotConstraint` | `SampledOneHotConstraint` |
| `"sos1"` | `Sos1ConstraintID` | `EvaluatedSos1Constraint` | `SampledSos1Constraint` |

Results include both active and retained removed constraints. Each row exposes
labels, `provenance`, `removed_reason`, and `removed_reason_parameters`. Sampled
rows expose `violations` and `feasible(atol=...)`, keyed by sample ID. Editing a
returned dictionary or snapshot does not update its owning result.

The same typed IDs appear in DataFrame indexes and context tables. For example,
`ConstraintID(1)` and `Sos1ConstraintID(1)` are different keys, and neither equals
`1`. Inputs whose family is fixed accept either an integer or the matching ID:
`constraints={1: constraint}` promotes the key to `ConstraintID(1)`, and
`instance.get_constraint_by_id(1)` looks up that regular constraint. An ID of
another family is rejected, even when it contains the same number. Returned
IDs, including dictionary keys, are always typed; ordinary Python dictionary
lookup still requires the typed key. Retain an attached constraint's
`constraint_id` or construct the appropriate ID when indexing a result.
Supplying both `1` and `ConstraintID(1)` as keys in the same input mapping raises
`ValueError`, since they would identify the same regular constraint.
`solution.constraint_violation(id)` requires a typed ID because its family
cannot be inferred from an integer alone.
IDs do not support `int()` or integer indexing conversion. Decision-variable
and sample IDs remain integers.
