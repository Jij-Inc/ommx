# Special Constraint Types

In addition to regular equality and inequality constraints, OMMX can retain Indicator, OneHot, and SOS1 constraints as distinct constraint types. A supporting solver can receive them through its specialized API without losing their meaning, while an Adapter that does not support them can use regular constraints produced by lowering.

```{important}
This page explains the mathematical meaning of each constraint type and how an Instance represents it. See the API Reference for each conversion method for the exact formulas generated by lowering, validity conditions, return values, exceptions, and atomicity.
```

## Three Special Constraint Types

| Constraint type | Mathematical meaning | Common use |
|---|---|---|
| {class}`~ommx.IndicatorConstraint` | Activate an equality or inequality constraint only when a Binary variable $z$ is $1$ | Conditional constraints |
| {class}`~ommx.OneHotConstraint` | Exactly one variable in a set of Binary variables equals $1$ | Select one of several alternatives |
| {class}`~ommx.Sos1Constraint` | At most one variable in a set is nonzero | Prevent the simultaneous use of several variables |

OneHot and SOS1 are similar but not interchangeable. OneHot means “exactly one,” so it does not allow every variable to be $0$. SOS1 means “at most one,” so the all-zero assignment is valid. OneHot variables are Binary, while SOS1 variables do not have to be Binary.

## Adding Them to an Instance

Create an Indicator by applying {meth}`Constraint.with_indicator() <ommx.Constraint.with_indicator>` to a regular {class}`~ommx.Constraint`. Create OneHot and SOS1 constraints with their dedicated types and the variables they contain.

```{code-cell} ipython3
from ommx import Instance, OneHotConstraint, Sos1Constraint

instance = Instance.maximize()
enabled = instance.new_binary("enabled")
choices = [instance.new_binary("choice", subscripts=[i]) for i in range(3)]

instance.objective = sum(choices)

# Enforce choices[0] + choices[1] <= 1 only when enabled = 1
instance.add_indicator_constraint(
    (choices[0] + choices[1] <= 1).with_indicator(enabled)
)

# Exactly one of the three choices is 1
instance.add_one_hot_constraint(OneHotConstraint(variables=choices))

# At most one of choices[1] and choices[2] is nonzero
instance.add_sos1_constraint(Sos1Constraint(variables=choices[1:]))
```

When a constraint is inserted, the Instance checks that every referenced decision variable exists and validates constraint-specific requirements, including that an Indicator's indicator variable and the variables in a OneHot constraint are Binary.

## Independent ID Spaces

Regular, Indicator, OneHot, and SOS1 constraints have independent ID spaces. For example, regular constraint ID `1` and Indicator constraint ID `1` identify different constraints. Always distinguish the constraint type as well as the integer ID when referring to a constraint.

The active entries for each constraint type are available through these properties.

| Constraint type | Property |
|---|---|
| Regular | {attr}`~ommx.Instance.constraints` |
| Indicator | {attr}`~ommx.Instance.indicator_constraints` |
| OneHot | {attr}`~ommx.Instance.one_hot_constraints` |
| SOS1 | {attr}`~ommx.Instance.sos1_constraints` |

## Native Support and Lowering

Each Adapter's `INPUT_CLASS` declares exactly which special constraints it accepts without conversion. For example, the PySCIPOpt Adapter sends linear Indicator and SOS1 constraints to SCIP's specialized APIs, but it does not accept OneHot constraints directly.

- See [Solve Special Constraints Directly with the PySCIPOpt Adapter](../tutorial/solve_special_constraints_with_pyscipopt_adapter.md) for passing special constraints to a supporting Adapter.
- See [Prepare an Instance for an Adapter](../tutorial/prepare_instance_for_adapter.md) for lowering special constraints to regular constraints for an Adapter that does not accept them.
- See [Adapter Exact Inputs (`INPUT_CLASS`)](./adapter_input_class.md) and [Instance Preparation and `PreparationPolicy`](./preparation_policy.md) for the responsibility boundary between exact inputs and Preparation.

The following APIs perform individual lowering operations explicitly.

| Constraint type | Lower one active constraint | Lower all active constraints |
|---|---|---|
| Indicator | {meth}`~ommx.Instance.convert_indicator_to_constraint` | {meth}`~ommx.Instance.convert_all_indicators_to_constraints` |
| OneHot | {meth}`~ommx.Instance.convert_one_hot_to_constraint` | {meth}`~ommx.Instance.convert_all_one_hots_to_constraints` |
| SOS1 | {meth}`~ommx.Instance.convert_sos1_to_constraints` | {meth}`~ommx.Instance.convert_all_sos1_to_constraints` |

The API Reference above owns the exact generated formulas, variable creation and reuse, validity conditions, returned IDs, and mutation contract on failure. In the standard Adapter workflow, use the recommended Policy and {meth}`~ommx.Instance.prepare` instead of manually composing individual conversion APIs.

The source constraint remains in the Instance as a removed entry after lowering. [Removed Constraints and Feasibility](./removed_constraints.md) explains the active/removed lifecycle, removal reasons, provenance, and feasibility with respect to the pre-transformation constraints.

## Accessing Evaluation Results

For {class}`~ommx.Solution` and {class}`~ommx.SampleSet`, select the constraint type evaluated by `constraints_df()` with `kind=`.

```python
solution.constraints_df()                  # regular
solution.constraints_df(kind="indicator")
solution.constraints_df(kind="one_hot")
solution.constraints_df(kind="sos1")
```

For Indicator constraints, `indicator_active` distinguishes a constraint that was satisfied unconditionally because its indicator was off from a constraint whose body was evaluated because its indicator was on.
