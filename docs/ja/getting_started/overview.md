# OMMXで何を共通化できるか

OMMXは、最適化問題と候補解にソルバーから独立した意味を与え、その上で使える操作を
共通化するプロジェクトです。ファイルの交換だけでなく、問題の評価、対応する変換、
変数値の復元、実行先との接続を繰り返し利用できることが採用の利点です。

## 一つのモデラーを使い続ける場合にも

モデラーで作った問題を、別のbackendでも使いたい、候補を一貫した基準で検査したい、
backendが直接扱わない制約を変換したい、といった作業があります。OMMXを共通の問題表現に
すると、連携する各ソフトウェアが同じ変換や結果の解釈を個別に持つ必要を減らせます。
モデラーを頻繁に切り替えることが前提ではありません。

| 担当 | 主な責任 |
|---|---|
| モデラー・業務アプリケーション | 業務上の意味、入力データ、問題構造を決め、OMMXの問題へ対応付ける |
| OMMX core | 変数・式・制約・候補評価の共通の意味と、公開契約を持つ変換・復元を提供する |
| Adapter | 直接受け取れる入力を宣言し、backendの入力へencodeし、返った候補をOMMXで評価する |
| backend | 探索・求解・サンプリングを行い、その実行方法に応じた結果や終了情報を返す |
| 利用者 | 目的に合う変換や設定を選び、対応条件と結果の保証が十分かを判断する |

例えばOneHotは「指定したBinary変数からちょうど一つを選ぶ」というOMMXの条件です。
その条件の意味は特定のソルバーのAPI名とは独立しています。対応backendへはその形で渡し、
必要なら通常の等式へloweringできます。意味の説明は[特殊制約](../user_guide/special_constraints.md)、
操作例は[Instanceを変換するHow-to](../how_to/transform_instance_without_solver.md)にあります。

## 問題を保ちながら、解くための表現を選ぶ

OMMXを「数理最適化のLLVM」のような共通基盤として考えると、ソースの問題構造、
使い回せる変換、実行先との接続を分ける方向性を捉えやすくなります。ただし、現在のOMMXが
任意の変換列を自動選択したり、意味を保証する汎用presolveをすでに提供したりする、
という意味ではありません。

このBookの公開b7例では、Instanceの構築・評価、特殊制約、InstanceClassに向けた
Preparation、対応する変換、Adapter経由の実行を扱います。個々の変換が何を保存するかは
同じではありません。[変換の保証](../user_guide/transformation_guarantees.md)で、
実行可能性・目的値・最適性を分けて判断します。

より業務に近い条件の追加や、複数の簡約操作を選択・反復するpresolve統合は将来の方向性です。
現在の対応機能・環境は[互換性と実行環境](compatibility.md)で確認してください。

## 必要な層だけ使う

問題の構築・変換・候補評価・Adapterの実行には、ArtifactもExperimentも必須ではありません。
問題や結果をファイルで保存・受け渡すときはArtifact、試行ごとの条件とデータを整理するときは
Experimentを追加できます。

- Pythonで使い始める：[インストール](install.md)から、目的に合うTutorialやHow-toへ。
- Rustや別の言語・ツールを接続する：[連携のDeveloper Guide](../developer_guide/integration.md)から
  共通概念と版の合ったAPI・仕様へ。Python Tutorialは前提ではありません。
- 操作の厳密な条件を調べる：[Reference](../reference/index.md)へ。
